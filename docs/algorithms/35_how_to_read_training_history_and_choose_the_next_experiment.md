# 35. 如何阅读训练历史，并决定下一轮实验该做什么

## 为什么这篇文档很重要

很多人在训练完一个模型后，第一反应是：

- 看一下 `accuracy`
- 看一下 loss
- 如果数字变好了，就觉得模型进步了

但在当前项目里，这样判断远远不够。

因为你面对的是：

- `session` 级切分的数据集
- 弱监督标签
- 两条模态链路：轨迹 + RD
- 很容易出现“整体数字不差，但某一类完全塌缩”的情况

所以，这个项目里真正重要的不是“训练完了没有”，而是：

> **你能不能从训练产物里读出模型到底学到了什么，哪里出了问题，下一轮应该改哪里。**

这篇文档就是专门讲这个问题。

---

## 第一部分：训练完成后，先看哪些文件

一个训练 run 完成后，你最常见会看到这些文件：

```text
artifacts/<run_name>/
├─ best_fusion_model.pt
├─ training_history.json
├─ training_metadata.json
├─ training_session_manifest.json
└─ evaluation_report.json
```

它们分别负责回答不同问题。

### 1. `training_history.json`

回答的是：

- 每个 epoch 的训练和验证表现怎么变化

你会看到：

- `train_loss`
- `train_accuracy`
- `train_macro_f1`
- `val_loss`
- `val_accuracy`
- `val_macro_f1`
- `learning_rate`

这是你判断“模型是在泛化，还是在过拟合”的第一入口。

### 2. `training_metadata.json`

回答的是：

- 这次训练到底用的是什么配置
- 当前 run 用了哪些 session 切分
- 当前标签顺序是什么
- 当前模型参数量是多少

很多时候你以为“模型变差了”，其实只是：

- `sequence_length` 改了
- `rd_input_channels` 改了
- `track_aux_loss_weight` / `rd_aux_loss_weight` 改了

所以这个文件是“解释这次实验为什么会变”的根依据。

### 3. `training_session_manifest.json`

回答的是：

- 哪些 session 属于 train / val / test

如果你要判断一轮结果有没有参考价值，这个文件必须看。

因为有时结果变化，不是模型改得更好，而只是：

- 测试集刚好更容易
- 或某一类 session 更难

### 4. `evaluation_report.json`

回答的是：

- 最终独立评估到底怎么样

它最重要，因为它通常对应的是：

- 当前 best checkpoint
- 当前测试集表现

你可以从这里看到：

- `accuracy`
- `macro_f1`
- `per_class`
- `confusion_matrix`

### 5. `reports/real/<run_name>/`

这里是图表层。

它最适合快速浏览：

- 曲线是否正常
- 混淆矩阵是否健康
- 哪些类明显拖后腿

## 第二部分：阅读训练历史时，正确顺序是什么

在当前项目里，推荐顺序不是“先看 train”，而是：

### 第一步：先看 `val_macro_f1`

这是最值得先盯的指标之一。

因为当前项目最容易出的问题是：

- 训练集越来越强
- 但验证集并没有真正变好

所以你首先应该问：

> `val_macro_f1` 是上升了，持平了，还是下降了？

### 第二步：再看 `val_loss`

这个指标告诉你：

- 模型在验证集上的置信度和错误程度

如果出现：

- `val_accuracy` 不低
- 但 `val_loss` 很高

通常意味着：

- 模型在某些错误样本上非常自信地预测错了

### 第三步：看 `train_macro_f1` 和 `val_macro_f1` 的差距

如果：

- `train_macro_f1` 很高
- `val_macro_f1` 很低

那通常是过拟合信号。

### 第四步：再看 `learning_rate`

很多时候某一轮突然变差，不一定是模型结构问题，也可能是：

- 学习率在这个阶段过高或过低

所以训练历史里的 `learning_rate` 不能忽略。

---

## 第三部分：怎么看一轮训练是“正常收敛”还是“异常收敛”

## 1. 正常收敛

比较健康的现象通常是：

- `train_loss` 逐步下降
- `train_macro_f1` 逐步上升
- `val_macro_f1` 虽然会波动，但总体上升或保持稳定

这说明模型不只是会记训练集，而是在逐步学会更可泛化的规律。

## 2. 过拟合

典型现象：

- `train_accuracy` 越来越高
- `val_macro_f1` 不涨，甚至下降

这说明模型更会拟合训练集，但没有学到更稳的边界。

## 3. 不稳定训练

典型现象：

- 某一轮很好
- 下一轮突然很差
- 再下一轮又恢复一些

这通常说明：

- 学习率不稳
- 小 batch 归一化不稳
- 输入表示还不稳定

## 4. 伪提升

典型现象：

- `accuracy` 提升了
- 但 `macro_f1` 没提升，甚至更差

这通常说明：

- 模型更偏向强类了
- 没有真正提升整体分类质量

---

## 第四部分：当前项目里，哪些信号说明“该改 RD”，哪些信号说明“该改轨迹链”

这是最实战的一部分。

## 1. 更像 RD 问题的信号

通常包括：

- 混淆矩阵里两类在谱结构上容易混，但轨迹统计其实差异明显
- 改完轨迹链后，结果还是主要卡在某两类的频谱区分上
- `Bird` 很好，但飞行器类互相混得很厉害
- ROI 对齐、物理轴、背景抑制一改，结果波动就特别大

这通常说明问题主导项还在 RD 链路。

## 2. 更像轨迹链问题的信号

通常包括：

- 测试集中某一类和另一类在速度层级上差异很大，但模型还是分不开
- 方向一变（接近/远离），模型就把类别学错
- 加强 RD 后，整体提升有限，但一加绝对速度特征就明显改善

这更像轨迹链仍然没有保住关键物理量。

## 3. 更像融合问题的信号

通常包括：

- `track-only` 和 `rd-only` 都还可以
- 但 fusion 后反而不稳定

这说明不是单模态不行，而是融合方式可能把其中一条模态带偏了。

## 第五部分：当前项目里，如何决定“下一轮实验改什么”

推荐用下面这个判断顺序。

## Step 1：先看测试集 `macro_f1`

如果没涨，先不要急着庆祝。

## Step 2：看 `per_class`

重点看：

- 有没有哪一类 `F1 = 0`
- 哪个类别拖后腿最严重

## Step 3：看混淆矩阵主方向

例如：

- `FixedWing -> Bird`
- `FixedWing -> RotaryDrone`
- `RotaryDrone -> FixedWing`

搞清楚主要错分方向，下一轮才能精准改。

## Step 4：把主错分方向和物理常识对照

例如你发现：

- 测试集里 `FixedWing` 的绝对速度很高
- `RotaryDrone` 的绝对速度中等
- 但模型还是混淆

那就说明：

- 模型没有很好利用绝对速度层级
- 或被其他不稳定线索盖住了

这时下一轮更应该补轨迹链，而不是继续盲目堆 CNN。

## Step 5：只改一到两个高价值点

不要一轮同时改太多东西。

因为你一旦：

- 同时改 RD 表示
- 同时改轨迹特征
- 同时改损失权重
- 同时改学习率

最后就很难知道到底是哪一步真的带来了提升。

在当前项目里，最好的实验通常是：

- 一轮只针对一个主问题下刀
- 然后重新比较混淆矩阵和 `macro_f1`

---

## 第六部分：什么时候应该保存 Git

在当前项目里，不是每一次训练都值得保存 Git。

更稳的标准应该是：

- `accuracy` 提升了
- `macro_f1` 也提升了
- 没有新增类别塌缩
- 主要混淆方向有改善

如果只是：

- 训练集更好了
- 或只有某个容易类别更好了

那通常还不值得作为里程碑提交。

## 第七部分：当前项目里，一次训练后最值得回答的 5 个问题

每次训练完，我建议你至少回答下面 5 个问题：

1. `macro_f1` 是提升了还是下降了？
2. 有没有类别 `F1 = 0`？
3. 混淆矩阵里主要错分方向有没有变化？
4. 这次提升更像来自 RD，还是来自轨迹链？
5. 下一轮最该改的是输入、模型、损失，还是切分与评估？

只要你每次都认真回答这 5 个问题，实验推进速度会快很多。

## 最后总结

在当前项目里，训练历史不是“跑完后顺手看看”的文件，而是：

- 你判断模型是否真正变好的依据
- 你定位问题来自哪条链路的依据
- 你决定下一轮实验怎么改的依据

一句话：

> **真正有价值的训练，不是多跑几轮，而是每跑一轮都知道下一轮为什么改、该改哪里。**
