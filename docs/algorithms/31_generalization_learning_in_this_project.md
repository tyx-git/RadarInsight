# 31. 当前项目如何进行泛化学习

## 为什么这个项目必须重视泛化

这个项目的目标不是把训练集记住，而是让模型在**新 session、新目标运动方向、新距离区间、新背景条件**下仍然能做出稳定判断。

对雷达识别任务来说，泛化尤其难，因为同一个类别在不同 session 里会同时发生这些变化：

- 距离变化：远近不同，能量强弱不同
- 速度变化：接近和远离时，多普勒正负号会变化
- 姿态变化：目标方位、俯仰和机动方式不同
- 背景变化：杂波、噪声、环境反射不同
- 采样差异：不同 session 的持续时间和轨迹长度不同

所以，当前项目里的“泛化学习”不是一句口号，而是从**数据切分、特征设计、模型结构、训练流程、评估方式**一路约束出来的。

## 当前项目是怎么做泛化学习的

### 1. 先从数据切分上防止“假泛化”

当前项目**不是随机打散 clip 再切 train / val / test**，而是按 `session` 级别切分。

也就是说：

- 训练集里的某个 session，不会同时出现在验证集或测试集
- 同一条轨迹切出来的相邻 clip，也不会被分到不同集合里

这样做的意义非常大。

如果把 clip 随机打散，模型很可能只是记住了同一个 session 的背景、能量模式和局部纹理，看起来精度很高，但一遇到新 session 就崩掉。这种情况不是泛化，而是数据泄漏。

所以当前项目把 **session 级切分** 当成泛化学习的第一道底线。

### 2. TR 轨迹链保留“变化”和“绝对量”两类信息

轨迹分支不是只喂原始 `range / azimuth / speed / snr`，而是同时构造两类信息：

- **变化信息**：`delta_range_m`、`speed_delta_mps`、`acceleration_mps2`、`turn_rate_degps`
- **绝对信息**：`clip_range_mean_m`、`clip_speed_mean_mps`、`clip_abs_speed_mean_mps`、`clip_snr_mean_db`

为什么要两类都保留？

- 只看变化，模型容易学到“形状像不像”
- 只看绝对量，模型容易过度依赖某个固定速度区间或距离区间

真正稳的泛化，通常来自两者结合：

- 一边看“这个目标怎么动”
- 一边看“这个目标大概处在哪个运动量级”

### 3. RD 微动链同时看局部 ROI 和全局上下文

当前 RD 输入已经不是单一局部图，而是双视角：

- **局部 ROI**：围绕目标中心裁剪，突出微动细节
- **全局上下文**：从整帧 RD 中下采样，保留背景和整体谱图结构

这一步对泛化很关键。

如果只看局部 ROI：

- 可能把目标切得过窄
- 容易丢掉全局速度结构和背景关系

如果只看全局图：

- 容易被大面积背景和杂波干扰
- 微动细节会被淹没

双视角的意义就是：

- 局部视角负责“看清楚目标”
- 全局视角负责“知道目标处在什么大环境里”

这比只依赖单一路径更有泛化能力。

### 4. 显式加入“符号不变性”

这是当前项目里非常重要的一条经验。

同一个目标：

- 朝雷达飞来时，径向速度可能是正的
- 远离雷达飞走时，径向速度可能是负的

但它的类别并没有变。

所以模型不应该把“速度正负号”本身学成类别定义。

为了解决这个问题，当前项目在两条链路都补了**符号不变信息**：

- 轨迹链：`abs_radial_speed_mps`、`abs_speed_delta_mps`、`clip_abs_speed_mean_mps`
- RD 链：`local_doppler_symmetric`、`global_doppler_symmetric`

这类特征的作用是：

- 让模型仍然能看到方向信息
- 但同时也能看到“忽略正负方向后，目标速度结构是什么样”

这会显著提升跨 session、跨运动方向的稳定性。

### 5. 训练和评估使用同一套轨迹归一化统计

很多项目会忽视这一点。

如果训练时和评估时使用不同的数据尺度，模型看见的就不是同一种输入分布，泛化结果会被污染。

当前项目已经把轨迹归一化改成：

- 只在训练 session 上拟合统计量
- 把 `track_feature_center` 和 `track_feature_scale` 保存进 checkpoint
- 评估时从 checkpoint 读回同一套统计量继续使用

这一步的意义是：

- 避免 train / val / test 泄漏
- 让泛化评估更真实
- 让模型在不同运行阶段看到一致尺度的特征

### 6. 小 batch 下使用更稳的时序归一化

当前训练常常是 `batch_size=4` 的 CPU 训练。

在这种情况下，`BatchNorm1d` 很容易不稳定，因为一个 batch 太小，统计量波动会比较大。

所以当前轨迹时序块已经改成更稳的 `GroupNorm`。

它的意义不是“模型更大”，而是：

- 小 batch 下更稳
- 不容易因为 batch 采样差异而抖动
- 对泛化更友好

## 当前项目里的泛化，不等于“万能泛化”

要非常清楚一点：

当前项目已经做了很多泛化设计，但它仍然受数据条件限制。

### 当前仍然存在的限制

- 标签仍然主要来自文件名，是 `session` 级弱监督
- 真实 session 总量还不够大
- RD 物理映射和 ROI 对齐虽然已经大幅增强，但仍是工程近似，不是上游严格标定真值
- 某些类别在不同 session 之间，速度分布和背景分布差异仍然很大

所以现在的泛化学习，更准确地说是：

> 在当前真实数据条件下，尽可能让模型学到跨 session、跨方向、跨背景都更稳的判别规则。

## 你应该如何判断“泛化有没有变好”

不要只看训练集精度，也不要只看单次 `accuracy`。

在当前项目里，更应该一起看：

- `Macro F1` 是否提升
- 混淆矩阵里是否还存在整类塌缩
- `Bird / FixedWing / RotaryDrone` 是否都至少能被识别到
- 新 session 上是否仍然稳定
- 更换一次训练 run 后，结果是不是大体一致

如果出现下面这种现象：

- 训练集精度很高
- 某一类在测试集完全为 `0`

那通常说明模型不是泛化了，而是学偏了。

## 如果你后续要继续提升泛化，优先级应该是什么

### 第一优先：继续增加真实 session 多样性

这是最根本的。

泛化不是靠模型硬猜出来的，最终还是要靠数据覆盖更多真实变化。

优先补的变化包括：

- 不同距离区间
- 不同飞行方向
- 不同背景场景
- 不同速度层级
- 不同 SNR 条件

### 第二优先：继续压实 RD 物理对齐

如果 RD 的物理轴和 ROI 位置仍然不稳，模型再复杂也会被错误输入拖偏。

### 第三优先：让轨迹链继续保留物理先验

尤其是：

- 速度大小
- 速度波动
- 轨迹跨度
- 机动程度

这些往往比“更深的网络层数”更能提升泛化。

### 第四优先：最后再去追更复杂的融合技巧

只有当前两条单模态链都已经比较稳时，更复杂的 fusion 才真正值得加。

## 一句话总结

当前项目里的泛化学习，本质上是在做三件事：

- **切分上防泄漏**
- **表示上保物理语义**
- **训练上保一致性和稳定性**

真正的高质量泛化，不是某一个技巧，而是这三件事同时成立。
